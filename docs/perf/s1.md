# S1 core-math performance and allocation gates

Local measurements for the S1 core-math hot paths. These are a local baseline
record, not a regression gate: the authoritative nightly numbers are CI
artefacts (see [`README.md`](README.md)).

- **Date:** 2026-10-01
- **Machine:** AMD Ryzen AI 9 365 (20 logical CPUs, 2.0 GHz base), 23 GiB RAM,
  Windows 11 Enterprise 10.0.26200
- **Toolchain:** MSVC 19.51.36256.0 (VS 18.9 BuildTools), CMake/Ninja Release
  (`benchmarks` preset), Google Benchmark 1.9.5, .NET SDK 10.0.401

## Benchmarks

Command (from `cpp/`, Release, `--benchmark_min_time=0.2s`):

```powershell
cmake --preset benchmarks
cmake --build --preset benchmarks
.\build\benchmarks\bin\cg_core_math_benchmarks.exe --benchmark_min_time=0.2s
```

| Benchmark | Operation | Time (ns/op) | CPU (ns/op) |
| --- | --- | ---: | ---: |
| `BM_QuatRotate` | `Quat::Rotate(Vec3)` | 35.9 | 34.0 |
| `BM_QuatSlerp` | `Slerp(a, b, t)` | 23.5 | 23.4 |
| `BM_PoseCompose` | `Compose(parent, child)` | 45.8 | 47.1 |
| `BM_ClockMap` | `ClockMapper::Map(sdk)` with a full window | 64.2 | 66.3 |
| `BM_PoseFromSdk` | `PoseFromSdk(float[7])` | 5.59 | 5.58 |

`BM_AbiVersion` (the S0 smoke benchmark) reports 2.21 ns/op. The numbers are
wall-clock per operation including the `DoNotOptimize` sink; they are not
comparable across machines and no absolute threshold is applied to them.

## Allocation gates

Both gates snapshot an allocation counter around a warmed-up 100k-iteration
loop that exercises `Quat::Rotate`, `Slerp`, `Pose` `Compose`/`Inverse`,
`ClockMapper::AddSample`/`Map` and `PoseFromSdk`. The counter snapshots, the
warm-up and every test-framework assertion live outside the measured loop.

### C++ — `cpp/tests/core-math/allocation_test.cpp`

The replaceable global `operator new`/`new[]`/`delete` family is overridden in
that translation unit with a `std::atomic<std::size_t>` counter. Correctness of
the counter was proven with a deliberate `delete new int(1);` probe inside each
measured loop first:

| Run | Result |
| --- | --- |
| Probe present (RED) | 5 tests failed; each reported `100000` allocations over 100000 iterations (one per probe) |
| Probe removed (GREEN) | 5 tests passed; delta `0` for every operation loop |

Command:

```powershell
.\build\windows-msvc\tests\cg_core_math_tests.exe --gtest_filter=AllocationTest.*
```

### C# — `dotnet/tests/CoreMath.Tests/AllocationTests.cs`

`GC.GetAllocatedBytesForCurrentThread()` is snapshotted around the warmed-up
measured loop. Correctness of the gate was proven with a deliberate
`new object()` probe (`GC.KeepAlive` so the JIT cannot stack-allocate it)
inside the loop first:

| Run | Result |
| --- | --- |
| Probe present (RED) | failed: `Core-math operations allocated 2400000 bytes over 100000 iterations` (24 bytes per probe) |
| Probe removed (GREEN) | passed: delta `0` bytes |

Command:

```powershell
dotnet test Cubeglass.sln --configuration Release --filter FullyQualifiedName~Allocation
```
